# Notebook photo import (v28 candidate, not released)

The October 2026 request is camera/photo transcription inside both flight forms. This change implements a mobile review screen and an authenticated Cloudflare reader on the Workers Free plan. It does not train a model, interpret tactics, add recommendations or infer missing notebook content. The real handwriting evaluation on October 18 exposed a release blocker: Luna recognizes the layout but cannot reliably transcribe the supplied cursive page. Do not describe this candidate as ready for production.

## Current boundaries

- `feature/notebook-photo-import` is local work based on `5f86b85` / v27. The production cadet app has not been changed. Local BUILD/VERSION are now v28/sortie-v28, and the release manifest has 39 verified files.
- The candidate public endpoint points to the exact Cloudflare reader. The deployed reader remains disabled; connecting the candidate is not permission to enable or push it. Local previews and test harnesses override the endpoint to empty; automated browsers also block the real reader URL. Offline pasted-text import works. No mock is shipped in the app.
- Text review uses the current user's actual editable questions, including custom names and IDs. Unknown/ambiguous mappings are left unselected. General highlights are not guessed onto individual exercises. Individual lines may be assigned to an existing exercise's brief focus or debrief notes.
- Acknowledgment is required before applying. Scalars fill only when empty; textareas append; exact duplicate list rows are skipped. Existing goal marks require their own opt-in. Brief/next-flight goals remain ungraded. Confirmed debrief grades use the existing carry semantics.
- Uncertain text, ambiguous marks and `[לא ברור]` spans receive no default destination. The user must correct/check and explicitly assign those rows. A sticky header provides close/photo comparison from a long review; comparison returns to the previous scroll position. Selecting a photo for comparison or resuming after a failed scan does not erase edited review text or require a paid reread. Completed reading focuses the section heading, not an input that would open the phone keyboard.
- Apply writes only the current local draft, after a recovery snapshot. Saved flights and the waiting-goal shelf change only through ordinary Save. Existing IDs, provenance, dates, course, untouched answers and uncommitted input buffers survive.
- Unapplied review text/assignments autosave inside that form's draft, including through reload. Ordinary Save excludes it from the saved record and retains a private draft if review work remains. Closing the import retains review text. Photos are not persisted. Selecting a new photo hides the old review until a new extraction or explicit text parse.
- Review text is included in the existing full draft backup. It is not added to the instructor cloud projection. Auth, settings schema, migrations, flight history and syllabus data have no changes.

## Backend and privacy

`worker/notebook.mjs` supplies literal extraction and validation; `worker/index.mjs` supplies the Cloudflare HTTP entry point and a SQLite-backed Durable Object. `/readNotebook` accepts only a JPEG data URL. The browser re-encodes a selected image, strips original EXIF/GPS metadata, and limits it to a 2400px longest edge. No flight history, notebook folder, email or custom questions are sent to the model. Image selection does not upload; the explicit Read action does.

The server validates a Firebase ID token using Google's `accounts:lookup` endpoint, checks current `validSince` revocation state and disabled status, then reads the user's own enrollment through the Firestore REST API using that same ID token. Existing Firestore rules still apply, including `authNotBefore` and the exact instructor UID pin. The reader has no Firebase administrator credential, reads no training records, and writes nothing to Firebase. It rejects absent/unrecognized origins, oversized/malformed images and unexpected input properties. Authentication/membership failures fail closed. Fresh issuance/authentication timestamps allow at most 60 seconds of clock skew; expiry and revocation cutoffs receive no grace. The live owner test exposed a one-second future timestamp, reproduced by a regression that still requires Google validation and rejects forged, expired and over-tolerance tokens. No rules or roster changes are needed.

Owner selected GPT Luna and authorized using his existing OpenAI API credit on 2026-10-14. Official documentation confirms `gpt-6-luna` supports image input, structured output and reasoning effort `max`; this is the configured choice. The saved OpenAI key and account model access were verified, and two actual image requests completed. The second matched all six expected checks on a synthetic typed Hebrew page after improving spelling/list-counter instructions. This is not handwriting accuracy evidence. The owner's reported $8.15 balance is unverified. No expensive-model fallback is permitted.

The Cloudflare environment variable `NOTEBOOK_ENABLED` must equal `true`, and the `SORTIE_OPENAI_API_KEY` secret must exist. Missing/disabled configuration is a kill switch. The checked-in configuration defaults to `false`. The model is fixed in server code; the frontend cannot override model, effort, output limits or instructions.

SQLite-backed Durable Object transactions reserve quotas before provider calls: 3 scans per minute and 20 per UTC day per user; 200 per day and 2000 per UTC month globally. Failed provider requests still consume quota. Storage contains only UID-keyed counters and time buckets, never photos/transcriptions, emails or tokens. Two active requests are admitted at a time. The outer Worker forwards the body without parsing it; image validation runs in the Durable Object, whose CPU allowance is suitable for the payload. A free-tier limit failure stops requests instead of upgrading the account or incurring hosting overages.

The provider key is a Cloudflare Worker secret, never client configuration. The candidate uses Responses with strict structured output, `store:false`, maximum reasoning, original image detail, a 32000-output-token cap (including reasoning), and a 300-second provider timeout; the client allows 330 seconds including authentication. The earlier 75-second/16000-token limits did not produce a complete result for the real page. Increasing the allowance enabled a complete response but did not fix handwriting accuracy. No automatic retries or more expensive fallback are configured. No tools/retrieval/fine-tuning are requested. Incomplete/refused/invalid responses cannot populate forms. Credential-bearing requests do not follow redirects. Worker observability is disabled and no application log includes tokens, image bytes or transcription text. OpenAI's abuse monitoring and image-input retention exceptions still apply; `store:false` is not a zero-retention guarantee.
